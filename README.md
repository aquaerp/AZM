# عزم (AZM) — نظام إدارة ورش السيارات

الإصدار الحالي: **1.2.1**. تخضع الإصدارات لسياسة موحدة موثقة في [`docs/release-process.md`](docs/release-process.md)، ويجب أن ينجح فحص بيانات الإصدار وبوابة الجودة قبل الدمج أو النشر.

تم تنفيذ المراحل التأسيسية وإدارة الورشة والمخزون والموظفين والمحاسبة والأرشفة: Django REST API، PostgreSQL، ومصادقة JWT مع أدوار المستخدمين (`مدير`، `فني`، `محاسب`) وإدارة العملاء والمركبات وبطاقات العمل وقطع الغيار والمهام والعمولات والفواتير والوثائق المشفرة.

## التشغيل المحلي

1. انسخ `.env.example` إلى `.env` وحدد `POSTGRES_PASSWORD` بقيمة محلية قوية.
2. انسخ `backend/.env.example` إلى `backend/.env` واستعمل بيانات PostgreSQL ذاتها.
3. شغّل قاعدة البيانات:

   ```powershell
   docker compose up -d postgres redis
   ```

4. ثبّت حزم Python (مرة واحدة) ثم نفّذ الترحيلات وشغّل الخادم:

   ```powershell
   .\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
   Push-Location backend
   ..\.venv\Scripts\python.exe manage.py migrate
   ..\.venv\Scripts\python.exe manage.py runserver
   ```

## بوابة العملاء

ينشئ المدير رابط متابعة آمن لكل بطاقة عمل من زر «رابط العميل». يعرض الرابط حالة الإصلاح والمركبة وموعد الإنجاز والفاتورة فقط، ولا يتطلب حساباً للعميل. يمكن إبطال رابط قديم وتوليد آخر عبر `POST /api/workshop/job-cards/<id>/rotate-portal-token/`. واجهة القراءة العامة هي `GET /api/portal/jobs/<token>/` ومحمية بمحدد طلبات للزوار.

تحتاج تكاملات WhatsApp/SMS وبوابات الدفع إلى مزود مُعتمد ومفاتيح وصول؛ لذلك لم تُفعّل تلقائياً في بيئة التطوير.

## المراقبة والتشخيص

- **فحص الصحة**: `GET /healthz/` يتحقق من اتصال قاعدة البيانات وRedis، ويعيد `200` عند السلامة أو `503` مع تفاصيل الخطأ عند تعطل أي خدمة. مفيد لمراقبة الحاويات (Docker healthcheck) وأدوات المراقبة الخارجية.
- **تتبع الأخطاء**: يدعم النظام [Sentry](https://sentry.io) عبر متغير `SENTRY_DSN`. عند ضبطه، تُرسل أي استثناءات غير معالجة في Django وCelery تلقائياً. اتركه فارغاً لتعطيل المراقبة محلياً.

## إدارة المنصة والاشتراكات

عند تسجيل الدخول من الواجهة الرئيسية بحساب Django superuser، ينتقل المستخدم تلقائيًا إلى لوحة إدارة المنصة. تعرض اللوحة مؤشرات الورش والاشتراكات والدخل الشهري المتكرر، وتدير خطط الأسعار وحد المستخدمين، وتربط كل ورشة بخطة وحالة وفترة اشتراك. حالات `suspended` و`cancelled` تمنع حسابات الورشة من تسجيل الدخول وتبطل جلساتها الحالية، بينما يبقى Django Admin متاحًا على `/admin/` للإدارة التقنية.

كل تسجيل عام جديد ينشئ تلقائيًا اشتراك تجربة لمدة 14 يومًا على خطة `trial-14-days`. التسجيل يرسل معرّف جهاز دائمًا من العميل، ويسجل الخادم HMAC لمعرّف الجهاز وIP دون حفظ القيم الخام؛ إعادة استخدام أي منهما ترفض تجربة جديدة حتى لو تغير البريد والاسم. لا يمكن لخادم ويب معرفة MAC الحقيقي عبر الإنترنت، ولذلك لا يعتمد النظام على ادعاء MAC قابل للتزوير. الورشة بلا اشتراك أو باشتراك منتهي/متأخر/معلق/ملغي تُرفض عند تسجيل الدخول وعند كل طلب JWT.
- **السجلات**: يكتب النظام سجلات مفصّلة (Console + ملف دوّار حتى 5 نسخ × 10MB) إلى `backend/logs/azm.log` (قابل للتخصيص عبر `AZM_LOG_DIR`)، وتُرسل تنبيهات بريد فورية لعناوين `ADMIN_EMAILS` عند حدوث أي خطأ خادم (500) كخط دفاع إضافي عند غياب Sentry.

## النسخ الاحتياطي والاستعادة

`scripts/backup.sh` ينشئ نسخة مضغوطة من قاعدة البيانات وأرشيف الوثائق المشفّرة مع ملف تحقق `sha256`، ويدعم رفعاً اختيارياً لتخزين خارجي عبر `rclone` وسياسة احتفاظ قابلة للتخصيص. `scripts/restore.sh` يعيد نسخة محددة إلى بيئة تشغيل (يتطلب تأكيداً تفاعلياً لأنه إجراء إتلافي). التفاصيل الكاملة وأمثلة الجدولة اليومية عبر `cron` موجودة في [توثيق نشر Hostinger](deploy/hostinger/README.md#النسخ-الاحتياطي-والاستعادة).

## التحقق من الجودة

لتشغيل فحوصات الإصدار المحلية الكاملة من جذر المشروع:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify.ps1
```

توجد بوابة CI مكافئة في `.github/workflows/quality.yml` وتشغّل اختبارات الخلفية بتغطية لا تقل عن 90%، وفحوص الويب والجوال، وبناء صورة Backend عند كل Pull Request أو دفع إلى `main` و`develop`.

يفحص الأمر إعدادات Django والترحيلات، ويشغّل اختبارات الخلفية مع تقرير التغطية، ثم يفحص الواجهة ويختبرها ويبني نسخة الإنتاج.
## اللغة

تدعم الواجهة العربية والإنجليزية. استخدم زر اللغة الظاهر في شاشة الدخول، لوحة الورشة، أو بوابة العميل؛ يُحفظ الاختيار في المتصفح وتتحول واجهة الاستخدام واتجاهها بين RTL وLTR. يُرسل الاختيار أيضاً في ترويسة `Accept-Language`، وتُنشأ فاتورة PDF باللغة المختارة عند توليدها.

## اختبار التحمل

يشغّل الأمر التالي اختباراً تمهيدياً معزولاً على قاعدة `azm_loadtest`، ويُنشئ لكل سجل عميلاً ومركبة وبطاقة عمل ثم يسجل معدل الطلبات وP50 وP95 والأخطاء في ملف JSON تحت `tmp`:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-load-test.ps1 -Records 100 -Workers 8
```

لتنفيذ سيناريو 100,000 سجل (300,000 صف جديد) في قاعدة الاختبار المعزولة فقط، استخدم `-Records 100000 -Workers 32 -FullScale`. لا يشغّل الاختبار على عنوان بعيد ما لم يُمرر خيار `--allow-remote` يدوياً إلى مشغل Python.
تفاصيل المراحل ومعايير القبول موجودة في [خطة اختبار التحمل](docs/load-testing.md).
