# خطة الوصول إلى النشر التجاري لنظام عزم

الحالة: قيد التنفيذ  
المدة التقديرية: 8–12 أسبوعًا  
المبدأ الحاكم: لا تُقبل أي ميزة ما لم تحافظ على عزل الورش وتطبق صلاحيات المستخدم داخل ورشته.

## المرحلة 1: خط الأساس وإدارة الإصدار

المدة: 3–5 أيام.

- اعتماد Git وفروع الإصدار وسياسة ترقيم النسخ.
- إضافة CI لاختبارات Django والواجهة والجوال وصور Docker وفحص التبعيات.
- تثبيت إصدارات التبعيات، وفصل بيئات التطوير وStaging والإنتاج.
- منع الأسرار من Git وتوثيق إنشاء الأسرار وتدويرها.

معيار القبول: بناء نظيف ومتكرر من الصفر، ونجاح بوابة CI كاملة، وعدم وجود أسرار في المستودع.

## المرحلة 2: عزل الورش الكامل

المدة: 1–2 أسبوع.

- جعل `workshop_id` حدًا أمنيًا إلزاميًا لجميع السجلات التشغيلية والمالية.
- مراجعة كل عمليات القراءة والتعديل والحذف والبحث والتقارير والملفات وWebSocket.
- التحقق من انتماء جميع العلاقات إلى الورشة نفسها.
- إضافة قيود قاعدة بيانات مركبة للأرقام والمعرّفات التي يجب أن تكون فريدة داخل الورشة.
- إنشاء اختبارات هجومية بورشتين تحاول كل منهما الوصول إلى بيانات الأخرى.

معيار القبول: جميع محاولات الوصول المتقاطع تعيد 403 أو 404، ولا يمكن إنشاء علاقة عابرة للورش، وتغطية المسارات الحساسة باختبارات عزل آلية.

## المرحلة 3: الصلاحيات داخل الورشة

المدة: 1–2 أسبوع.

- فصل مالك الورشة عن المدير والمحاسب والفني وموظف الاستقبال.
- الانتقال إلى صلاحيات على مستوى الإجراء، مثل إصدار فاتورة وتسجيل دفعة وصرف مخزون.
- منع المستخدم من تعديل دوره أو ورشته.
- فرض انتقالات حالات صحيحة للبطاقات والفواتير والمهام.
- إضافة سجل تدقيق للقيم قبل وبعد، والمستخدم والورشة والوقت وعنوان IP.
- إبطال الجلسات عند تعطيل المستخدم أو تغيير صلاحياته.

معيار القبول: مصفوفة صلاحيات معتمدة، واختبارات إيجابية وسلبية لكل دور ولكل عملية حساسة.

## المرحلة 4: الجاهزية التجارية والأمنية

المدة: 2–3 أسابيع.

- إصلاح PDF العربي داخل Linux ودعم الفواتير متعددة الصفحات.
- إضافة بيانات المنشأة ومتطلبات الفوترة الإلكترونية السعودية وZATCA بعد اعتماد مختص.
- منع تعديل الفواتير الصادرة واستخدام الإشعارات الدائنة والمدينة.
- معالجة ثغرات Expo/Metro وفحص الملفات المرفوعة وإضافة MFA للحسابات الحساسة.
- إعداد الخصوصية وشروط الاستخدام والاحتفاظ والتصدير والحذف.

معيار القبول: لا ثغرات عالية أو حرجة، وفاتورة عربية ناجحة داخل Docker ومعتمدة مهنيًا ونظاميًا.

## المرحلة 5: Staging والاختبارات التشغيلية

المدة: 1–2 أسبوع.

- إنشاء Staging مطابق للإنتاج وإصلاح فحوص الصحة عبر Caddy.
- تفعيل المراقبة والبريد والتنبيهات وتشغيل migrations بصورة محكومة.
- تشفير النسخ الاحتياطية واختبار الاستعادة الفعلية وتحديد RPO وRTO.
- اختبارات E2E والحمل وتعدد الورش وفشل PostgreSQL وRedis وCelery.
- توقيع تطبيق سطح المكتب واختبار نسخ Android وiOS على أجهزة حقيقية.

معيار القبول: نجاح UAT مع ورشتين على الأقل، والاستعادة ضمن RPO/RTO، وعدم وجود عيوب حرجة أو عالية.

## المرحلة 6: الإطلاق المرحلي والاستقرار

المدة: 2–4 أسابيع.

- إطلاق داخلي، ثم ورشة Pilot، ثم 3–5 ورش، ثم التسجيل بالدعوات، ثم الإطلاق العام.
- تقييد إدارة المنصة وتفعيل MFA وسجل وصول الدعم إلى بيانات العملاء.
- مراقبة أخطاء API وP95 وCelery والتخزين والنسخ الاحتياطية ومحاولات العبور بين الورش.
- اعتماد Runbook للحوادث وSLA والصيانة وآلية rollback.

معيار القبول: 14 يومًا بلا حادث عالي الخطورة، واستعادة حديثة ناجحة، واعتماد تقني وأمني وتجاري موثق.
