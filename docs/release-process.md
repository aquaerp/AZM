# سياسة الإصدار والنشر

## الفروع

- `main`: الإصدار الموجود أو الجاهز للإنتاج، ويحظر الدفع المباشر إليه بعد ربط المستودع البعيد.
- `develop`: تجميع التغييرات المقبولة للإصدار التالي.
- `feature/<name>` و`fix/<name>`: تغييرات محدودة تدمج عبر Pull Request.
- `hotfix/<name>`: إصلاح عاجل يبدأ من `main` ويعاد دمجه في `develop`.

## بوابة القبول

لا يدمج أي تغيير ما لم تنجح بوابة `Quality Gate` كاملة: اتساق رقم الإصدار، فحص الأسرار، فحوص Django والترحيلات، تغطية الخلفية 90%، اختبارات وبناء الواجهة، فحص الجوال، بناء سطح المكتب، وبناء صورة Docker.

يجب على Pull Request أن يصف أثر التغيير، طريقة اختباره، أي migrations، وخطة التراجع. تتطلب تغييرات المحاسبة والصلاحيات والنسخ الاحتياطي مراجعة ثانية.

## إنشاء إصدار

1. حدّث `VERSION` وأرقام الإصدارات في حزم الويب والجوال وسطح المكتب.
2. انقل البنود المناسبة من `Unreleased` في `CHANGELOG.md` إلى قسم الإصدار وتاريخه.
3. شغّل `python scripts/check_release_metadata.py` ثم `scripts/verify.ps1`.
4. ادمج Pull Request الإصدار في `main` بعد نجاح CI.
5. أنشئ وسمًا موقّعًا باسم `v<version>` واربطه بصفحة إصدار تحتوي تعليمات الترحيل والتراجع.
6. انشر أولًا إلى Staging، نفّذ فحص الدخان، ثم خذ نسخة احتياطية قبل نشر الإنتاج.

## التراجع

- احتفظ بصورة الحاويات ووسم Git للإصدار السابق.
- إذا لم تتضمن النسخة migration غير قابلة للعكس، أعد نشر الوسم السابق وشغّل فحص الصحة.
- عند وجود تغيير بيانات غير قابل للعكس، أوقف النشر واستعد النسخة المأخوذة قبل الإصدار وفق `deploy/hostinger/README.md`.
- لا تنفذ استعادة على الإنتاج قبل التحقق من checksum وتجربة النسخة في Staging.

## الحماية المطلوبة عند ربط GitHub

- اجعل `main` و`develop` محميين.
- امنع الدفع المباشر والحذف وفرض مراجعة واحدة على الأقل.
- اطلب نجاح جميع وظائف `Quality Gate` ومحادثات المراجعة قبل الدمج.
- فعّل Secret Scanning وDependabot والتنبيهات الأمنية.
